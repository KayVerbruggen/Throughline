The LLM client foundation (`src/llm/`). A deliberately narrow, provider-agnostic `LlmClient` interface — one `complete(prompt)` call in, one text result out, no chat history or streaming — with a direct-fetch Anthropic implementation, chosen by a `createLlmClient()` factory that mirrors the storage layer's runtime split. Configuration (API key + model) lives in `localStorage`, scoped to the app's webview profile rather than the project folder, so the key never lands in the user's git repo. Failures are returned as a Result rather than thrown, matching the Expression Engine, so feature code can surface them inline. Its UI so far is the settings dialog (a gear in the top bar) where the key and model are entered and a "Test connection" button exercises the client end-to-end (the gear also carries a dot while no key is set), plus a guard-suggestion affordance in the Behaviour view.

On top of the client sit two feature-enabling pieces. `completeJson` wraps `complete` for structured tasks: it extracts JSON from the reply, validates it with a caller-supplied function, and retries once with the error fed back so the model can self-correct — the caller's validator is where *semantic* checks live, so those failures also drive the retry. The first feature built on it, guard suggestion, turns an alternate branch's plain-language condition into a formal guard: the validator resolves any proposed new component variables, augments a clone of the project with them, and type-checks the guard with the Expression Engine's `analyzeGuard`, so an invalid guard is never offered. A guard may propose *new* variables (not just reuse existing ones); accepting creates them and sets the guard together. Still to build on this base: effect suggestion, prototype drafting, and reverse-engineering.
