In declaring the variables a component carries, facing modelling each observable sign as its own variable lets the model represent states the real system forbids, and forces an activity for every combination of them, we decided to declare one variable over the states that can actually occur whenever two candidate variables can never vary independently and not to keep one variable per observable and rely on flows never to set an illegal combination to achieve an illegal state cannot be written down, and the activity set stays proportional to the real state space rather than its square, accepting that the variable no longer maps one-to-one onto a thing you can point at in the field.

## Worked example

The Signal Lights (C-007) began as two variables, one per physical sign:

```
upper: red | green
lower: red | green
```

Four representable states for a domain that permits three — both-green is the
exact safety violation the lights exist to prevent, and the model could write it
down. Worse, because the two varied independently, every combination needed a
named activity: *show green at the upper reach*, *show green at the lower reach*,
*show red at the upper reach*, *show red at the lower reach*, *show red*, *show
red on both reaches*. The last two had byte-identical effects.

Replacing them with one variable over the states that can occur:

```
permits: neither | upper | lower
```

collapses seven activities to four. "Show red at the upper reach" stops existing,
because red-at-a-reach is not an action — it is the consequence of permitting the
other reach, or neither. Both duplicates disappear, because they are now the same
single assignment.

## How to spot it

Two variables on one component that never legally vary independently. The
practical tell: **you find yourself writing an activity whose effects set both of
them together.** That activity is doing the work the type should be doing.

## What this does not fix

This only applies when the variables are genuinely mutually exclusive. *Halt all
actuators* (ACT-006) sets `upstreamGate.state := closed` and
`downstreamGate.state := closed` — two components, genuinely independent state,
nothing to collapse. Naming a compound action like that still means restating its
parts, which is a real gap in the model rather than a modelling mistake.

A related limit: once the state is one variable, a state-dependent action wants to
be a single assignment from another variable (`signalLights.permits :=
interlockController.chamberLevel`). Effects already allow that — an effect's
right-hand side is a full expression, and an enum takes the same enum. Here it
does not apply, because `chamberLevel` is `upper | lower | mid` and the third
value means something different from `neither`; the chamber sitting mid-level is
not the same fact as the signs both showing red. So FL-006 keeps a guarded branch,
which is the honest encoding. The type mismatch asking that question is the system
working, not fighting it.
